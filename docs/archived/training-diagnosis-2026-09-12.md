# 2026-09-12 自博弈退化诊断

本文记录修复前的实现和实验。后续修复、验证结果见 [自博弈修复验证记录](selfplay-validation.md)；不能把本文的旧实现描述当作当前行为。

## 结论与范围

检查对象是 `b10000.pt`、`sp01/latest.pt`（日志到 iteration 4）、`sp02/latest.pt`（到 iteration 1），以及当前 Python/Rust 实现。已完成代码核查、搜索反馈对照和 36 局模型对照；本次未修改训练或引擎行为，也未覆盖模型文件。

目前不能把问题归结为“模拟次数不够”。已确认：

1. `sims=64, mcts_batch=64` 只有一批非终局叶子反馈，反馈到达时选步所用的访问次数已经确定，搜索不能据此修正选步。
2. 引擎有额外的永久破产规则：连续两次无生产性动作即标记破产，此后只允许 Pass，时代计分时清零。搜索又在展开时修改同一计数，可能比实际执行提前判死。
3. 训练一直使用最新模型采集下一轮数据；评估失败不回滚。搜索策略不可靠时，policy loss 下降并不意味着棋力上升。

## 1. 实验结果

每组 4 局，seed 为 91000–91003，网络座位依次为 0–3，其余三个座位均为 heuristic。MCTS 使用 `sims=64, c_puct=0.25, prior_top_k=32, max_depth=10, q_init=True`；所有组关闭根噪声、确定性选步。Policy 组直接选择网络最大 logit。

表内为网络座位的平均终局 VP；括号为其被标记破产的局数。

| 模型 | Policy 直接选步 | MCTS batch=64 | MCTS batch=8 |
| --- | ---: | ---: | ---: |
| b10000 底座 | 108.25（0/4） | 77.25（1/4） | 117.75（0/4） |
| sp01 latest | 102.00（0/4） | 85.50（0/4） | 71.00（1/4） |
| sp02 latest | 102.25（0/4） | 96.25（0/4） | 114.25（0/4） |

解释边界：这是诊断样本，不是有统计把握的棋力排名。固定发牌 seed 不等于完整复现：当前 Rust 搜索和观测 determinization 使用额外随机源。本实验足以复现“底座经搜索也能走到破产”，也表明修改 batch 并不能保证已经训练过的模型恢复。

底座 checkpoint 元数据记录：10000 局模仿、2 epochs、`min_vp_filter=30`，当时 heuristic benchmark 胜率 10%、网络均分 106.2。它不是未经训练的随机网络，也不能仅凭低分就要求重新生成底座。

## 2. 搜索反馈为何失效

位置：`engine/src/ai/nn_mcts.rs:279`（收集一批模拟）、`:317`（统一回传价值）、`:333`（按访问次数选择）。

流程为：根节点先取 policy/Q → 收集一批模拟并增加访问次数 → 网络计算叶子价值 → 回传价值 → 若模拟预算耗尽，按访问次数选步。

因此 `64/64` 的常规非终局分支只展开到根节点下一手；叶子 V 不参与任何后续选择。根节点 policy、Q 初始化和噪声仍会影响访问次数，所以它也不等价于纯 policy argmax。提高 `max_depth` 无法解决“下一批根本没有发生”的问题。

对于 `256/64`，常规非终局路径大致只有四批反馈/展开机会，并不自动搜索到 `max_depth=10`。深度按全桌单个行动计算，不是当前玩家的完整回合数。

隔离验证使用固定非并列 policy、关闭 Q 初始化、关闭 Top-K，以排除剪枝并列排序的干扰；只反转根节点之后的叶子价值：

| 配置 | 网络调用行数 | 反转叶子价值后访问次数是否变化 | 最终选步是否变化 |
| --- | --- | --- | --- |
| 64 sims / batch 64 | 1, 64 | 否 | 否 |
| 64 sims / batch 8 | 1, 8, 1, 1, 1, 1, 1, 1, 1 | 是 | 是 |

这也解释了低模拟配置为何特别快，以及 `reuse 0/0`：没有深入到下一批可复用的子节点，并不证明搜索质量良好。

此外，`select_child` 将尚未收到价值的访问计入分母，使已访问但待反馈分支的 Q 暂时变成 0；在正负都有的效用尺度上，0 对负价值分支反而更乐观。这需要结合 pending visit 的处理一起修正，不能仅把它解释为温和的虚拟损失。

## 3. 0 分的实际路径与规则问题

在 `b10000 / batch64 / seed91003 / seat3` 的对局中：

- 运河阶段多次借贷，收入降到 -9；铁路开始时已有 24 VP。
- 铁路首轮连续两次借贷，收入降至 -10。
- 第三轮还剩 £4 时执行研发，现金归零。
- 第四轮连续 Pass、Scout 后被标记 `is_bankrupt=True`，当时仍显示 24 VP。
- 随后只允许 Pass，最终 VP 为 0。

规则位置：

- `engine/src/gameplay/rules.rs:83`：执行动作后累计无生产性行动；达到 2 即永久破产。这里的“生产性”排除 Pass 和 Scout，不要求负收入或现金为零。
- `engine/src/gameplay/legal_moves.rs:22`：破产后仅返回 Pass。
- `engine/src/gameplay/scoring.rs:81`：时代结算直接把破产玩家 VP 设为 0。

这套永久淘汰/清零机制没有出现在仓库 `brass-birmingham-rules.md` 的欠款规则中。该文档描述的是卖板块偿付，再扣除欠款对应 VP。不能把额外规则产生的 0 分全视为正常的策略得分。

搜索还存在两处独立不一致：

1. `nn_mcts.rs:428` 在**展开节点、尚未行动**时递增 `consecutive_stalled_actions`；随后 `apply_move` 再递增。根节点 priming 也会经过这一逻辑，因此模拟可能早于实际游戏判破产。
2. `nn_mcts.rs:402,775` 在轮到任一破产玩家时把分支当作终局，给该玩家硬编码 -2.5，其他玩家则使用当时已记入的 VP 差。真实对局仍继续，其他人的终局得分尚未确定；该向量也不保证零和，与训练的终局效用契约不一致。

修复应先明确游戏规则，统一真实执行与搜索路径，避免在搜索展开时另写一套状态转移。

## 4. 日志不能直接推出的结论

### `samples` 下降不全是坏局

`mp_selfplay.py:73–91` 对三个非学习座位分别抽签。`heuristic-opponent-prob=0.25` 是**每个对手座位**的概率，并不是整局有 25% 概率混入教师。第一轮混合局概率为 `1 - 0.75^3 = 57.8%`。

之后历史池可用，默认 `mm_prob=0.25` 加入抽签，每个对手座位有 50% 概率不是当前网络；混合局概率成为 `1 - 0.5^3 = 87.5%`。只要混入任一对手，代码就仅采集一个指定 learner 的动作，即使其他座位仍使用当前模型。

因此第二轮开始样本量本身就会下降。破产座位不再采样、整局低分过滤也可能进一步减少样本。当前配置每个 worker 只打 2 局，`learner=gi % 4` 使混合局指定 learner 只覆盖座位 0、1，未轮换到 2、3。

### `min_vp=0` 不证明这些局已进入训练

`selfplay.py:439` 的低分过滤会返回 `([], vps)`，汇总 VP 时仍纳入这些分数。工作区里 CLI 默认过滤阈值已由 20 改为 0；本次保留了该用户修改。旧运行未保存完整参数，所以无法从现有日志确定当时使用的是哪个默认值。

因此不能断言这些训练已经把所有 0 分局喂入模型。反过来，把过滤阈值提高也不能修复搜索或规则，还可能让强化学习失去失败轨迹的负价值监督。

### `arena 0%` 与整体 VP

- `arena_games=0` 的轮次实际上未评估，应显示 `--`，不能作为战绩。
- 真正评估的 sp01 iteration 2 为 2/16，sp02 iteration 1 为 0/16；确实未达到晋升门槛，但局数小且缺乏相同设置下的训练前基线。
- `avg_vp` 混合所有座位、所有对手角色；对局 seed 和角色组成也会变化，不是固定对手下当前网络的平均得分。
- 单个玩家被清零就能大幅拉低全桌均分；应同时记录零分率、破产率、学习座位分数、有效采样局数、角色构成及被过滤局数。

## 5. 训练循环如何放大问题

`selfplay_loop.py:468` 每轮都把当前模型加入历史池，无论是否晋升。下一轮也总用当前模型继续自博弈，best 只用于对战评估。弱搜索标签 → policy 拟合弱标签 → 弱模型生成下一批标签，是当前实现允许的退化链条；并不是 loss 越低、棋力就越高。

当前 warm start 只加载权重，优化器以 `lr=1e-3` 重新开始；早期 buffer 只有数百至千余个相关样本，每轮反复训练两遍。这是需要消融验证的遗忘风险，尚不能断言学习率就是本次退化的主因。温度默认 0.8 也可能增加风险，但本次关闭温度和噪声后仍复现破产，所以不是充分解释。

另有续训隐患：初始 best 仅在内存创建，只有晋升时才写出 `best.pt`。当前两个 run 均无 `best.pt`；直接 resume 时会把 latest 作为新的 best 参考，丢失原来的底座基准。这不解释已经发生的退化，但会污染后续判断。

## 6. 修复与验证顺序

1. **先修规则与搜索一致性**：明确永久破产/清零是否符合项目目标；消除搜索重复修改停滞计数、伪终局价值，与真实执行保持一致。
2. **让低模拟预算真正获得搜索反馈**：减小或自适应搜索 batch，正确区分 pending/completed visits，并增加实际深度、完成价值回传次数的诊断。`64/8` 可作为对照起点，不是棋力保证。
3. **补齐指标和 best 持久化**：分别记录模型/教师/历史模型的分数，失败与过滤原因，完整配置、评估前基线；修正 learner 座位轮换和混合局采样的无谓丢弃。
4. **再验证学习是否有增益**：从原底座新建实验，先固定发牌/座位比较 policy、MCTS、关闭 Q 初始化的 MCTS；只有搜索确有增益时，再做短程自博弈。学习率可对照 `1e-4`、每轮 1 epoch；温度与其他参数单独消融，不一次全改。
5. 对评估中 VP 并列也应统一使用官方排序结果；当前 arena 的“winner 判断 OR argmax(VP)”可能把错误的并列首位算作胜者。

不建议继续把 sp01/latest 当作已经验证的主力模型训练，也不建议仅提高 min-VP 过滤或加大 sims 来掩盖异常。
