# 09 · 演进方向全景：从哪里继续提升

> **本章目标**：闭环转起来之后，"变强"的具体杠杆有哪些？本章把所有演进方向分成五个层面（度量 / 数据 / 网络 / 搜索 / 工程）逐层盘点——每个方向讲**现状 → 瓶颈 → 怎么验证值不值得做**——最后给一套实验方法论和一棵决策树。
>
> 主读文档：[roadmap.md](../roadmap.md)（阶段规划，本章与它的近期/中期/远期一一对应）、[ai-advise.md](../ai-advise.md)（长期设计原则）、[ai-action-encoding.md §7](../ai-action-encoding.md)（风险分层）。
> **贯穿原则**（ai-advise.md 原话的转述）：*先由错误案例证明瓶颈，再投入复杂度。* 本章每个方向都按这条原则给出"验证手段"。

## 9.1 把"变强"翻译成工程问题：三层风险模型

[ai-action-encoding.md §7](../ai-action-encoding.md) 把整个系统抽象成一条链，风险自上而下分三层：

```text
1. Candidate Generator   搜索只看到全合法集的一小部分——好动作根本没进候选集?
2. Action Representation 特征编码把"执行不同、价值不同"的动作折叠成同一行?
3. Pointwise Scorer      打分头缺候选间交互,表达不了"互斥/竞争"关系?
```

**为什么这个模型重要**：网络涨不动时，新手会先怀疑"网络太小/训练太少"（第 3 层），但本项目的实测结论（v4 复测，2026-08）是第 2 层已基本干净（剩余碰撞全部执行等价），**第 1 层（候选生成器）才是最大风险**。诊断顺序错了，投入就错了。9.2 的 candidate recall 就是第 1 层的度量工具。

---

## 9.2 度量先行：永远先要一把更好的尺子

所有演进决策的质量 = 评测体系的质量。按优先级：

### ① candidate recall（第 1 层风险的直接度量，roadmap 近期第 2 条）

**定义**：已训练策略对全合法集做一次前向，它的 top-1/top-3 是否落在候选生成器的 shortlist 内。若 recall 很低 = 网络经常认为"shortlist 之外的某个动作更好"——搜索一直在错过它们，**生成器就是当前天花板**。

实现思路（零件都在）：`materialize_sample` 恢复全合法候选（01 章）→ `net.policy_value` 对全候选打分 → 与 `heuristic_candidates` 的 shortlist 求交集比例。这是**第一个值得写的分析脚本**。

### ② held-out teacher validation（roadmap 近期第 1 条）

06 章的 `evaluate_policy` 指标跑在**训练用的同一批 shard** 上——只能看"拟合"，不能看"泛化"。做法：留出 5~10% 对局的 shard 从不参与训练，专门做验证集。机器学习的标准动作，成本几乎为零。

### ③ value 校准

rank 头预测的 `1−rank` 与真实终局名次的偏差分布（04 章的 rank MSE 只是标量均值）。按局面特征（剩余回合数、双方差距）分组看误差——MCTS 的叶子评估全靠它，它不准则搜索越深越自信地错。

### ④ 引擎侧批量评测工具

`docs/engine-tools.md` 里有两个现成工具：`sweep_scores`（批量 seed 扫描出 CSV）和 `mcts_lab`（MCTS 基准 / 局面检查 / 参数 sweep）。**固定 seed 区间 + 大样本**的版本对比就用它们——比手工跑 benchmark 严谨得多（roadmap 中期第 3 条的"评估纪律"）。

### ⑤ 更远：Elo / 联赛（未建）

版本多了以后，"打两两对抗"是 O(n²) 的。Elo 制的内部联赛（每个 checkpoint 一个等级分）是规模化的正确姿势——8.5 的门禁对局就是它的数据来源。属于"版本数 ≥10 再建"的基础设施。

## 9.3 数据侧：喂什么决定长成什么样

### shortlist hard negatives（roadmap 近期第 3 条）

现状：imitation 的 policy 目标集中在教师选择的等价类上。问题：**训练时的候选分布和 MCTS 推理时的候选分布不一致**。改进方向：向训练候选里加入"被教师排除但分数不低"的备选（负样本给 0 或低目标），让网络学会"为什么不是它们"。

### teacher 退役路径（roadmap 中期第 2 条）

8 章闭环转稳后，policy 目标来源逐步从 heuristic teacher 换成 MCTS visit 分布（05 章）。不是二选一：**混合比例随迭代衰减**是平滑的退役路径。退役完成 = 真正的 AlphaZero 阶段；同时 8.7 里"对 teacher 的 top-k"指标换成"对历史版本网络的 top-k"。

### 人类对局数据（阶段 4 的隐藏红利）

项目阶段 4（TTS 数据抽取）落地后，真人盘面能反向流入训练管线：

- **imitation 资产**：真人高分局可作为额外教师——比 heuristic 老师天花板更高；
- **eval 资产**：固定真人局面集做"局面重现"回归测试（网络在该局面的排序与真人选择对比）——比随机对局基准更能暴露具体短板；
- **分布现实检验**：self-play 的开局分布会越走越窄（8.8 反模式 3），真人数据把分布拉回现实。

### reward shaping（roadmap 远期第 3 条，谨慎）

给经济/VP 差加中间奖励可以加速早期学习，但**永久改变"争第一名"的目标函数**是危险的。roadmap 的立场：仅当需要时用 potential-difference 形式、λ 随训练衰减。新手最容易在这里翻车——把网络训成"经济最大化机器"而不是"赢家机器"。

## 9.4 网络侧：表示与容量

### 容量 scaling（便宜的第一杠杆）

`NetConfig` 全部是超参：`trunk=256`、`graph_layers=3`、`action_emb=128`…加大一档的代价是线性的，收益需要 A/B（9.7）。经验顺序：先加 `graph_layers`（连通性推理是 Brass 核心，03 章的钩子），再动 `trunk`。**但记住 9.1：如果瓶颈在候选生成器，扩容量是在错误的层上花算力。**

### 候选间 self-attention（encoding §7 第 3 层风险的完整解）

03 章的集合上下文是 O(N) 的折中；若错误案例集中在"互斥候选间的微妙权衡"，完整解是候选间 attention（O(N²)）。全合法集 N 可达数千——这是为什么它被列为"需要时再投入"：先有错误案例，再考虑用 shortlist 内 attention 这类折中。

### 表示升级（roadmap 远期第 1/2 条，ai-advise.md 的 State Representation 一节）

现状盘点（ai-advise.md 原话）：地图连通性**已是**图结构；但玩家全局量、手牌、历史仍是 flatten vector。两个升级方向：

- **手牌/历史 token 化**：把 35 维手牌槽位、历史动作序列变成 token 序列——当错误案例集中在"卡牌保留价值 / 对手竞争"判断时再做；
- **belief 表示**：用公开历史（已出现卡牌、对手动作约束）建模**对手手牌分布**，替代纯 `determinize()` 的独立随机采样（05 章 5.2）。这是不完全信息建模的深水区，收益大、复杂度大。

### schema 升级纪律（encoding §9）

以上任何表示改动都必须 bump schema version 并过 §9 的维护清单（02 章）——这是本项目防止"旧权重无声作废"的制度保障，演进时严格遵守。

## 9.5 搜索侧：把推演做得更聪明

### 参数杠杆（便宜，先用尽）

`sims`（质量单价）、`candidate_k`（候选宽度，0 = 全合法）、`batch_size`（GPU 攒批）、`c_puct`（探索系数）、`max_depth`——`mcts_lab` 的 sweep 模式（9.2 ④）就是为扫这些参数准备的。**注意 sims 与训练阶段的联动**（8.8 反模式 4）：先低后高。

### 算法升级（当前代码库没有，方向性知识）

- **并行 MCTS / virtual loss**：当前 Rust 搜索攒批评估叶子，但树内仍是串行模拟。virtual loss 允许多线程同时探索同一节点的不同分支——吞吐的下一个数量级，工程量在 Rust 侧；
- **置换表（transposition table）**：Brass 里不同行动序列常到达同一局面，共享子树统计 = 免费的等效 sims 提升；
- **更聪明的 determinize**：与 9.4 的 belief 表示是同一枚硬币的两面——采样对手手牌时按公开信息约束（已知打过的牌不在其手里），比纯随机更接近真实分布。

## 9.6 工程侧：吞吐与产品化

### self-play 吞吐分析

`mp_selfplay.py` docstring 的分工设计值得细读：**worker 全部 CPU 推理**（网络太小，每步成本被 Python/Rust 簿记主导，8-16 个进程互不抢 GPU），**GPU 留给主进程训练**。分析瓶颈的方法：看 8.7 的局长/局数耗时分布——CPU worker 排队（加 worker）还是 GPU 训练排队（减 `train_steps` 步数或加大 `materialize_workers`）？吞吐优化的第一步永远是**测量哪个队列在堆积**。

### serving 路径：通往阶段 4/5

`replay_worker.py`（06 章 6.7）已验证"checkpoint → 决策服务"的完整链路：加载 checkpoint → stdin/stdout JSON 应答 Rust 的 `choose` 请求（[replay-design.md](../replay-design.md) 的协议），支持 `mcts` / `policy` 两种模式并返回 evidence。产品化（roadmap 阶段 4/5）就是三步：

1. **TTS 数据抽取**：Lua 脚本读公共盘面 + 己方手牌 POST 到 localhost（对手手牌不可读——与训练时 determinize 的隐藏信息假设一致，见 05 章 5.2）；
2. **推荐服务**：复用 replay_worker 链路，**延迟预算 10~15 秒**——用 `mcts_lab bench` 校准"预算内能跑多少 sims"（sims 就是 8.8 说的质量单价，这里变成了实时约束）；
3. **UI 悬浮窗**：PySide6 置顶窗展示 Top-3 建议 + 预估收益，数据源是 evidence。

注意训练↔服务的角色差异：训练要的是吞吐（慢点无妨、批越大越好），服务要的是延迟（单局面、预算硬约束）。同一个网络，两种调参。

## 9.7 实验方法论：怎么知道一个改动值不值得

这套方法论适用于本章所有方向，也是 8.8 反模式 5 的正面展开。

**① 一次只改一个变量。** 换超参的同时换 seed 区间 = 实验作废。

**② 固定评测协议并写成脚本。** 版本对比 = 固定 seed 区间 + 固定对局数 + 固定 sims + 轮换座位，一条命令出数（`sweep_scores` / 8.5 的 gate 函数）。凡是"这次我手工跑了 20 局感觉强了"的结论都不可信。

**③ 显著性意识。** 4 人局随机基线 25%；games=40 的粒度 2.5%。差异小于两三个粒度 = 没有结论，只有噪声（05 章 5.5）。

**④ 建立基线快照。** 每个实验开始前，把当前最佳版本的全套指标（8.7 的表格）跑一遍存档。没有基线的提升百分比都是编的。

**⑤ 实验日志。** 一行一个实验：日期 / 改动（含具体值）/ 评测协议 / 结果 / 结论。三个月后你会感谢它——AI 训练的实验数量远超直觉，记忆不可靠。

**⑥ 何时停止一个方向**：连续两三次实验都在噪声区间内 → 该方向的边际收益已尽，回 9.1 换层找瓶颈。**持续提升的真相是轮换瓶颈**：候选生成器 → value 质量 → 搜索深度 → 数据多样性……每次只解当前最粗的管子。

### 为什么不是 PPO / actor-critic（roadmap 中期第 4 条）

强化学习还有另一大流派：不做搜索，直接用策略梯度（PPO）训练。roadmap 把它排在"self-play + search 稳定之后"是正确的工程判断：**AlphaZero 路线在本项目还未被榨干**（self-play 顶层入口都还没建），换范式意味着丢掉 MCTS 推演带来的"训练目标优于当前策略"的红利，换取生成吞吐——这是瓶颈转移到生成侧之后的取舍，不是现在的。

## 9.8 决策树：下一步该做什么

把本章收敛成一棵查询树（与 roadmap 的近期/中期/远期对应）：

```text
Q1 闭环能稳定转起来吗?(08 章)
 └ 不能 → 先建门禁入口(8.6),别急着改算法

Q1 能。candidate recall 测过吗?(9.2①)
 └ 没测 → 写 recall 脚本。这是当前最大风险项的直接度量
 └ recall 低 → 瓶颈 = 候选生成器:扩 candidate_k / 短列表 hard negatives(9.3)
 └ recall 高 → Q2

Q2 验证集指标还在涨吗?(9.2②)
 └ 在涨 → 什么都不用改,加大数据量与迭代数(最无聊但最有效的答案)
 └ 平台期 → Q3

Q3 benchmark vs heuristic 到 50%+ 了吗?
 └ 没到 → 门禁闭环 + teacher 退役(9.3),让 self-play 发力
 └ 已过 → Q4

Q4 错误案例集中在哪里?(逐个分析输棋对局)
 └ 搜索深度不够 → 搜索侧(9.5):sims 预算 / virtual loss / 置换表
 └ 互斥候选权衡错 → 网络侧(9.4):set-attention / 扩容量
 └ 卡牌保留/对手判断错 → 表示侧(9.4):token 化 / belief
 └ 吞吐不够迭代太慢 → 工程侧(9.6)
```

**一条元规则**：当你需要在这棵树里犹豫超过十分钟，通常说明缺的是 9.2 里的某把尺子，而不是某个改进本身。

## 练习

1. **写 candidate recall 脚本**（9.2①，本章最有价值的一次动手）：对一批 full-legal imitation shard 物化全合法候选，用 bootstrap checkpoint 打分，统计 top-1/top-3 落在 `heuristic_candidates` shortlist 内的比例。得到你的项目第一份"生成器上限"报告。
2. **held-out 验证**（9.2②）：重新生成 shard 时留出最后 10% 不训练，对比训练集/验证集的 `evaluate_policy` 指标——两者的差距就是你过拟合程度的第一个实测值。
3. **吞吐画像**（9.6）：跑一轮 `SelfPlayPool.generate`，分别记录"生成总耗时 / 局"和 `train_steps` 的"步/秒"，算出闭环里生成与训练的时间占比——它决定你该优化哪一侧。
4. **决策树实操**：对着 9.8 走一遍你的项目现状，把"当前节点"和"下一步动作"写进实验日志（9.7⑤）的第一行。
